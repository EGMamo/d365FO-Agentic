# D365 Finance & Operations notes

## Supported target

The MVP targets a **Tier-2 (or higher) sandbox** environment reachable at `https://<name>.sandbox.operations.dynamics.com`. Development VMs (Tier-1) work as well when reachable over the network.

## Authentication

Pick one of two routes:

- **No MFA (simplest):** a dedicated test account that is not subject to MFA. In a test tenant this usually means excluding the account from Conditional Access, or turning off Entra *security defaults* for the tenant, which is what Microsoft's FastTrack Playwright setup guide does. Turning off security defaults is a tenant-wide security change: prefer a non-production tenant, and do not do it for a shared or production tenant.
- **MFA account:** sign in once yourself with `session-login` (below) and reuse that browser session. FastTrack's F&O JMeter sample takes the same approach for MFA accounts: it injects already-obtained F&O session cookies instead of scripting the sign-in.

The default auth flow uses **username / password** for a non-MFA test account. This is the pragmatic choice for automated runs.

Alternatives (not implemented in the MVP but planned):

- Device-code flow with an Entra ID user.
- Service principal + certificate for OData / Custom Service calls (out of scope for UI testing).

Store credentials only in `.env` — never in test-case files. **Quote any value that contains `#`** (`D365_PASSWORD='Ab12#@!z'`): unquoted, the `.env` parser reads everything from the `#` on as a comment, so only the part before it is typed into the sign-in page. `doctor` reports this, and `run` refuses to start on a truncated credential, because repeated wrong-password attempts can lock the test account.

## Safety

These are enforced in code, not just requested in the prompt:

- **Production is refused.** `run` stops when `D365_BASE_URL` is, or looks like, production. LCS-managed sandboxes (`<name>.sandbox.operations.dynamics.com`, also with a region such as `.eu`) and dev VMs (`*.axcloud.dynamics.com`) pass; `<name>.operations[.geo].dynamics.com` is treated as production. **Power Platform (unified) sandboxes use that same host format**, so declare them with `D365_ENVIRONMENT_TYPE=sandbox` (`doctor` shows whether the type was declared or guessed). `AGENT_ALLOW_PRODUCTION=true` is the explicit override for a real production run.
- **Legal entity.** Destructive operations belong inside the test's legal entity (`legalEntity` in the test case, else `D365_COMPANY`, default `USMF`). A model-requested URL whose `cmp=` differs is refused. Switching company through the UI is still up to the model and the prompt.
- **Navigation.** Model-requested navigation is limited to the F&O host and Microsoft sign-in hosts; add others (an ADFS server, `lcs.dynamics.com`) with `AGENT_ALLOWED_HOSTS`. Redirects the browser follows itself are not intercepted.
- **Tool allowlist.** The Playwright MCP server exposes about 70 tools, including cookie and storage dumps, arbitrary JavaScript and file access. Only navigation, snapshot, click/type/fill, tabs, dialogs, waits and the `verify_*` assertions are exposed, plus Learn search/fetch. Add more with `AGENT_ALLOWED_TOOLS_EXTRA` (for example `playwright__browser_file_upload` for a DMF import test).
- **Dry-run mode** (`--dry-run` / `AGENT_DRY_RUN=true`) skips state-changing browser tools (click, type, fill, press, drag, upload, dialogs, select, and JS/route tools if opted in). Navigation and snapshots still run so the model can see pages.
- **Audit.** Refused calls are recorded as `policyBlocks` in `results.json` and shown in the HTML report. An attempt with 5 refused calls is stopped.
- Every action is captured in structured step reports and can be replayed from `results.json`.

## Selector strategy

The agent is prompted to prefer **accessibility snapshots** and **semantic locators** over brittle CSS or coordinates. The Playwright MCP `browser_snapshot` tool returns an accessibility tree with `ref` identifiers used by every interactive tool.

Learned selectors are persisted to the local knowledge base under `kind: "selector"` and retrieved on subsequent runs of related tests.

## Fast navigation and known-good paths

Two things keep the agent from exploring the F&O UI on every run:

- **Direct page links.** `d365_open_menu_item` opens a form by its display menu item (`<D365_BASE_URL>/?cmp=<legal entity>&mi=<MenuItem>`), waits for the "Please wait" overlay to clear and returns a snapshot, all in one model turn. That replaces the five to ten clicks and snapshots of the navigation pane, and does not depend on menu captions. The URL goes through the same navigation guardrails as `browser_navigate`, and the company is always the test's legal entity.
- **Known-good path.** When a case passes, the browser actions it took (pages opened, element names clicked or typed into, keys pressed; never typed values or refs) are saved in the knowledge base as that case's known-good path. The next run of the same case gets the path in its prompt and follows it instead of working the steps out again. A newer passing run replaces it.

The built-in page list covers common starting points (All vendors, All customers, All sales orders, All purchase orders, Released products, General journals, Main accounts, All projects, Users and a few more; see [`src/d365fo/navigation.ts`](../src/d365fo/navigation.ts)). To teach it more pages, open the page in F&O, copy the `mi=` value from the address bar and add it to `<KB_DIR>/menu-items.json` (default `./knowledge/menu-items.json`):

```json
[
  { "mi": "WHSWaveTemplateTable", "label": "Wave templates", "path": "Warehouse management > Setup > Waves" },
  { "mi": "VendTableListPage", "label": "Kreditoren", "aliases": ["Alle Kreditoren"] }
]
```

An entry with the same `mi` as a built-in replaces it (useful for captions in another language). Test steps can also name the menu item directly ("Open menu item WHSWaveTemplateTable"). The built-in names follow standard F&O; they were not checked against a live environment here, so correct any that differ in yours with the same file.

## Speed on complex forms

Besides direct links and known-good paths:

- **Control names as targets.** Playwright MCP is started with `--test-id-attribute data-dyn-controlname`. F&O puts
  the AOT control name on each control in that attribute (the name Task Recorder records), so actions resolve to
  `getByTestId('SystemDefinedNewButton')`-style locators that hold across languages, releases and personalisation.
  Playwright MCP accepts a locator as `target`, so the model can act on a known control without a snapshot.
- **Learned forms.** Controls used on each form are learned live into `knowledge/pages.json` and offered the next
  time the form opens; see [Self-learning](self-learning.md#learning-fo-forms-while-it-works).
- **Busy overlay.** After a click, typing, a selection, a key press or a dialog, the run calls
  `browser_wait_for` until "Please wait" is gone (it returns at once when the overlay is not shown). A locator target
  that does not match yet is retried once after that wait. `AGENT_FNO_AUTO_WAIT=false` turns both off.
- **Element timeout.** `PW_ACTION_TIMEOUT_MS` (default 15 s, Playwright's default is 5 s) gives slow forms time to
  render before an action fails.
- **Smaller snapshots.** Anonymous wrapper nodes, of which F&O has many, are dropped from snapshots
  (`AGENT_SLIM_SNAPSHOTS`), and the prompt points the model to `browser_find` and partial snapshots.
- **RSAT habits.** The prompt follows Microsoft's RSAT guidance: type values into lookups instead of picking a list
  position, and filter grids to find a record instead of assuming the selected row
  ([RSAT tutorial](https://learn.microsoft.com/dynamics365/fin-ops-core/dev-itpro/perf-test/rsat/rsat-tutorial)).
  Deep links follow Microsoft's format and only work for menu items that allow root navigation
  ([Create deep links](https://learn.microsoft.com/dynamics365/fin-ops-core/dev-itpro/user-interface/create-deep-links)).

Verified here against a local page that mimics F&O markup (control-name attributes and a "Please wait" overlay) with
Playwright MCP 0.0.83: a first visit learned both controls, a second visit opened the form by caption and used them
without a snapshot. The control-name attribute and title format still need confirming on a real sandbox.

## Waits, verification and traces

- **Time budgets:** every tool call is bounded (`AGENT_TOOL_TIMEOUT_MS`, default 60 s; navigation `AGENT_NAV_TIMEOUT_MS`, default 90 s; an explicit `browser_wait_for` is never cut short). A call over budget is reported to the model and recorded under `timeouts` in `results.json` and the report. The values are starting points taken from FastTrack's Playwright sample, not tuned on F&O.
- **Verified results:** when a step has an `expected` result, the agent must report it `passed` with `verified: true` after checking a fresh snapshot. A case whose expected results were not checked ends `blocked` ("not counted as passed"), not `passed`. Dry runs are exempt.
- **Recorded values:** the agent can save created ids and numbers with `record_value`; they appear as `data` in `results.json` and in the HTML report.
- **Traces:** with `PW_TRACE=on-failure` (default) or `on`, the agent starts and stops a Playwright trace around each attempt (the MCP server needs `--caps devtools`, added automatically). Trace files under `reports/playwright-output/traces/` are attached to failed attempts; a passing attempt's trace is deleted with `on-failure`. Open one with `npx playwright show-trace <file>.trace` (not verified here).

## Signing in with a saved session (optional)

Instead of keeping a password in `.env`, sign in once yourself and let runs reuse that browser session. MFA works because you complete it.

1. `node dist/cli/index.js session-login` opens a headed browser on `D365_BASE_URL`. Sign in, wait for the F&O dashboard, then close the window. The session is saved to `.d365fo-session/storage-state.json` (owner-only permissions, gitignored).
2. Set `D365_STORAGE_STATE=.d365fo-session/storage-state.json` in `.env`.
3. Runs load that session into an isolated browser context (the file is never modified). If `D365_USERNAME` / `D365_PASSWORD` are also set they remain the fallback when the session has expired; otherwise the affected step is blocked.

`doctor` reports whether the session file exists, is readable, and looks expired: all dated cookies expired, no cookies for the D365 host, or older than `D365_SESSION_MAX_AGE_HOURS` (default 12). A missing `DynamicsOwinAuth` or `ms-dyn-csrftoken` cookie is only a warning (a file with only Entra cookies may mean the sign-in never reached F&O; the cookie names come from FastTrack's JMeter sample and are not confirmed on every deployment). Cookie values are never printed.

F&O session cookies have no expiry date, so file age is a weak signal. `doctor --probe` asks the server: it sends one GET to `D365_BASE_URL` with only the saved cookies for that host (no browser, redirects not followed, session file untouched) and reports `LIVE` or `EXPIRED` (redirected to the Microsoft sign-in page, or 401/403). An expired result fails `doctor` unless username and password are set as a fallback. An unreachable host is reported but is not treated as an expired session. The probe is off by default, so plain `doctor` stays fast and offline for this check.

For run-time fail-fast, `run --probe-session` performs the same check before test execution starts and aborts immediately when the session is expired or the host is unreachable.

Assumption to verify on a sandbox: the cookie names and the redirect-to-sign-in behaviour come from the FastTrack JMeter cookie sample, not from a documented contract. The community posts on how these cookies are obtained were not readable when this was written.

### Sign-out policy

The agent never signs out of a saved session: the prompt tells the model not to use the user menu, `/Logout` or End sessions, because that would invalidate the session later runs reuse. Password logins are also left signed in; F&O frees the user session on its own timeout. An optional sign-out step for password logins is not implemented. Each user counts against the per-user session limit, so parallel runs should use separate accounts or saved sessions.

The file contains live session cookies: treat it like a password, never commit or share it. Leaving `D365_STORAGE_STATE` empty keeps the previous password-only behaviour.

## Entra app registration (optional)

An Entra ID app registration (client id and secret) lets the agent read F&O data through OData, signed in as the app
instead of a user. It does **not** sign in to the F&O web client: Microsoft sign-in for the browser needs a user, so
browser steps still use `D365_USERNAME` / `D365_PASSWORD` or a saved session.

What it adds:

- A read-only agent tool, `d365_odata_query`, to confirm data a step created or changed (for example that vendor
  `V-1001` now exists in `VendorsV2`). Queries are GET only, limited to 50 rows, and the entity name is validated.
- Test cases that only check data can run with the app registration alone; any step that needs the F&O pages is then
  reported blocked, saying no user sign-in is configured.
- `doctor` gets a token and makes one request (`LegalEntities`, one row) to prove F&O accepts the app.

Setup:

1. In the Azure portal, register an app (single tenant) and create a client secret.
2. In F&O, open **System administration > Setup > Microsoft Entra ID applications**, add the client id and map it to a
   user whose roles allow reading the entities your tests check. Keep that user's rights read-only where you can.
3. Set `D365_TENANT_ID`, `D365_CLIENT_ID` and `D365_CLIENT_SECRET` (in a profile or `.env`). The token is requested
   for `<D365_BASE_URL>/.default`. For sovereign clouds set `D365_AUTHORITY_HOST` (for example
   `https://login.microsoftonline.us`).
